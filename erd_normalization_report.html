3. Comprehensive Database Normalization Report Theory & Validation

The Luna's Pharmacy database schema has been designed following strict relational modeling principles to ensure data integrity, prevent anomalies, and optimize transaction performance.

First Normal Form (1NF) — Elimination of Repeating Groups ✓ Compliant

Criteria: Each column contains atomic (single, indivisible) values, and each record is uniquely identifiable by a primary key.

  • Atomic Data: All columns store single primitive scalar values (integers, fixed-point decimals, strings, timestamps).
  • No Multi-Valued Fields: Multiple purchased medicines are never stored as comma-delimited strings or JSON lists within sales. Instead, each individual purchased product is placed in a dedicated row in the child table sale_items.
  • Unique Rows: Every table incorporates an explicit auto-incrementing Primary Key (id).

Second Normal Form (2NF) — Elimination of Partial Dependencies ✓ Compliant

Criteria: The table must be in 1NF, and all non-key attributes must depend on the entire primary key (no partial functional dependency).

  • Single-Column Primary Keys: All 6 tables utilize a single-column surrogate primary key (id INT/BIGINT AUTO_INCREMENT PRIMARY KEY).
  • Zero Partial Dependencies: Because none of the tables use a composite (multi-column) primary key, partial key dependencies are mathematically impossible. Every non-key attribute is fully dependent upon the single primary key id.

Third Normal Form (3NF) — Elimination of Transitive Dependencies ✓ Compliant

Criteria: The table must be in 2NF, and no non-key attribute can depend on another non-key attribute ($X \to Y \to Z$). Non-key columns must depend only on the primary key.

  • Independent Entities: Staff profile attributes (role, status) reside strictly in users; product master data (barcode, price, stock) and categories reside strictly in products and categories.
  • Referential Links Only: Relational tables store only foreign keys (user_id, sale_id, product_id, category_id) rather than repeating vendor, staff, or category details.
  • Derived Values Are Computed: Line totals, sale gross, and sale net are calculated from sale_items.qty and sale_items.price when the report is read; no derived column is stored in sales or sale_items.
4. Specialized Retail & POS Design Patterns Industry Best Practice

In retail pharmacy and point-of-sale environments, certain apparent redundancies are deliberate, standard architectural decisions required for legal, fiscal, and audit immutability:

1. Point-in-Time Historical Price Freeze (sale_items.price)
While products has a price field, sale_items.price captures the exact selling price at the moment of checkout. If the pharmacy adjusts the retail price of Paracetamol next month from ₱8.00 to ₱10.00, past receipts and monthly tax reports must legally remain at ₱8.00. Therefore, sale_items.price is functionally dependent on the transaction line item, not the current master catalog price.
2. Derived Totals Are Computed, Not Stored (sale_items.qty * sale_items.price)
Line totals, sale gross, and sale net are calculated when the report is read, from the stored quantities and prices. There is no stored total, gross, or net column, so a price change in the catalog can never rewrite a past receipt.
3. Names Are Resolved Through Relationships (stock_movements)
The stock log no longer copies product_name or recorded_by. Each row keeps product_id and user_id, and the current names are read by joining products and users. A deleted product shows as "Deleted item" and a missing user shows as "Unknown user".
4. Legacy Compatibility Field (products.category)
The old category text column is kept so older pages keep working. The normalized link is category_id to categories(id). Once every page reads the foreign key, the text column can be dropped.
5. Summary for Academic & Technical Defense Quick Reference
Question / Criterion Technical Answer
What Normal Form is the database in? The database is in Third Normal Form (3NF).
Why is price in both products and sale_items? It is a Point-in-Time Historical Snapshot to protect fiscal records from future price modifications.
Where do gross and net come from? They are computed from sale_items.qty * sale_items.price when the report is read, so there is one source of truth and no stale totals.
What happens if a product is deleted? The stock log keeps the movement with product_id set to NULL and shows "Deleted item", so the audit history is never lost.
How is referential integrity enforced? Via foreign keys with CASCADE (sales → items), RESTRICT (products → items), SET NULL (products → stock movements), SET NULL (users → stock movements), and SET NULL (categories → products).
